# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

A single-page personal portfolio site (Kshitij Bachhav) built with React 19 + Vite + Tailwind CSS 4, animated with Framer Motion. No backend, no router, no state library — it's one scrollable page assembled from section components.

## Commands

- `npm run dev` — start Vite dev server (default `http://localhost:5173`)
- `npm run build` — production build to `dist/`
- `npm run preview` — serve the production build locally
- `npm run refresh:posts` — re-bake the offline copy of the Medium posts into `portfolioData.js` (optional; the live site doesn't depend on it)
- `npm run refresh:repos` — re-bake the offline copy of the GitHub project archive into `portfolioData.js` (optional; same deal)
- `npm run make:charts` — redraw the two featured-project figures in `public/` from the benchmark numbers held in `scripts/make-project-charts.mjs` (only needed when a benchmark is re-run)

## Pages

Two Vite entries (see `build.rollupOptions.input` in `vite.config.js`): the main site (`index.html` → `src/main.jsx`) and a standalone resume page (`resume.html` → `src/resume.jsx` → `ResumePage.jsx`). The resume is typeset from `portfolioData.js` and has a print stylesheet (`src/components/resume.css`) — "Download PDF" is just `window.print()`. The main site hides the native cursor globally for `CustomCursor`; `resume.css` restores it on the resume page, so any new page without `CustomCursor` needs the same override.

There is no lint script, no test runner, and no TypeScript configured in this repo.

## Architecture

**Single-page composition.** `src/App.jsx` renders one document: `Navbar`, then a `<main>` with `Hero → About → Skills → Projects → Contact` sections separated by a `Divider`, then `Footer`, plus fixed-position overlay components (`CustomCursor`, `EasterEgg`) mounted at the root. Sections are plain `<section id="...">` elements; the id (`home`, `about`, `skills`, `projects`, `contact`) is the anchor used for both nav scroll-spy and `scrollIntoView` navigation — keep those ids in sync between `Navbar.jsx`'s `navItems` and each section component.

**Content lives in data, not JSX.** `src/data/portfolioData.js` is the single source of truth for skills, featured projects, achievements, and contact info (email/LinkedIn/GitHub) — it's a plain JS module exporting arrays/objects consumed by `Skills.jsx`, `Projects.jsx`, and `Contact.jsx`. To add/edit a featured project or skill category, edit this file, not the component markup. Project entries reference images by path (e.g. `/project-saas.png`) served from `public/`.

**The projects section is two tiers, and only the top one is authored.** `projects` holds the three case studies the resume leads with; each is built around a `metrics` array of exactly three measurements, because this work is backend and a screenshot would misrepresent where the effort went (`image` is optional and renders in the body as supporting evidence, not as the headline).

Two of the three have no screenshot to give, so their `image` is a **figure drawn from their own benchmark run** — `scripts/make-project-charts.mjs` writes both SVGs into `public/`, and the numbers live in that script rather than in the markup, so a re-run of a benchmark is a one-line edit and `npm run make:charts`. The charts follow the data-viz rules that matter here: one measure per chart so there is no legend and colour never carries identity; a linear axis from zero (Pulse's slowest path is 14× its fastest, and that ratio is the finding); the reserved status red used only for the strategy that actually loses money, never as a second series; and the failing bar marked with a glyph and a sentence, so the meaning never rests on the colour. The series hue is a stepped-down `--color-accent` (`#0099ba`, not `#00d4ff`) — the site's cyan sits at OKLCH L 0.80, outside the band a large filled mark wants on a dark surface, and a 400px block of it glares. Set `imageAlt` on any entry whose image is a chart; the fallback alt is "<title> preview", which is right for a screenshot and useless for a figure. Everything else is the archive below it, which is generated — see the next section. A featured project's `repo` field must match its GitHub repository name exactly; that's what keeps it from also appearing in the archive.

Each case study is a **bounded card on a pinned horizontal track** (`FeaturedScroller.jsx`): a wrapper N×100vh tall holds a sticky viewport-height frame, and scroll progress through it drives the track's `translateX`, so scrolling down moves the cards sideways. Inside a card the layout is unchanged — identity, date, stack and the three metrics on the left; description, bullets, tags and links on the right.

Three constants carry the design, and each is there because its absence looked broken:

- **`CARD_MAX` / `LANE`.** A card is capped at 1100px (`.content-container`'s measure) and never wider than `vw - 2 × LANE`. Full-bleed 100vw cards were the original bug: with no edges, mid-transition you saw one case study's prose beside the next one's metric rail with nothing between them, which reads as a broken page rather than as two cards passing. `LANE` is 190px because the SectionPath ribbon and the dock nav both live out there — a wider card put its metric labels behind the dock icons.
- **`HOLD`.** The scroll→track map is detented, not linear: each card holds its centred position for a stretch of scroll and the moves happen in between. That reads as snapping without taking the scroll away from the user. The track deliberately does **not** auto-advance — auto-forwarding carousels measurably hurt comprehension, and anything self-moving past five seconds owes the user a pause control (WCAG 2.2.2). The progress ticks under the track are that control instead: click one to scroll to that card.
- **The opacity/scale falloff is flat through the middle and steep at the edges** (`[i-1, i-0.6, i, i+0.6, i+1]`). A linear ramp dimmed *both* cards to ~60% halfway through a move — the whole screen went dark at the moment there was most to look at. The dim's job is to mark the subject when a card is parked off-centre; mid-move there is no subject.

`.track-mask` fades the track's outer 120px so the peeking neighbour dissolves into the gutter instead of sliding under the dock nav. It must sit on a **static** wrapper: a mask painted on the moving track would travel with it and fade the middle of a card as it passed.

Below `lg`, under `prefers-reduced-motion`, and before hydration, the same cards render as a plain vertical stack — a viewport-width card on a phone is unreadable and horizontal pinning fights touch scrolling. Known cost, stated plainly: off-screen cards are translated out of view rather than unmounted, so find-in-page can't usefully scroll to them and tabbing into one jumps the page. That's inherent to the pattern, not to this implementation.

**Two sections are live, not authored: writing and the project archive.** Both follow the same shape — a Vercel function under `api/`, an edge cache, a `use*` hook, and a build-time fallback in `portfolioData.js`. `Writing.jsx` renders whatever is on Medium right now. `useMediumPosts.js` fetches `/api/medium`, a Vercel serverless function (`api/medium.js`) that reads the RSS feed **server-side** — medium.com sends no `Access-Control-Allow-Origin` header, so the browser can never fetch that feed directly, and every public CORS proxy is rate-limited or intermittent. The response is cached at Vercel's edge for 5 minutes with `stale-while-revalidate`, so a newly published article appears within ~5 minutes with no edit and no redeploy.

Three consequences worth knowing before touching this area:
- **`posts` in `portfolioData.js` is a fallback, not the source of truth.** It renders instantly on load and stays on screen if the feed request fails, so the section is never empty. Editing it does not change what a visitor normally sees.
- **`postOverrides` (keyed by canonical article URL) is where per-post polish goes** — a better `tag` or `blurb` than Medium's own. It is merged over both live and fallback posts, so the two render identically. Feed `<category>` slugs are title-cased automatically (`crude-oil` → `Crude Oil`).
- **`api/_feed.js` is shared** by the serverless function, the dev middleware, and `scripts/refresh-posts.mjs` — parse fixes belong there. The leading underscore is what stops Vercel from routing it as its own endpoint. `vite.config.js` mounts that same handler at `/api/medium` during `npm run dev`, so local dev exercises the real path instead of silently falling back.

`Projects.jsx`'s archive works the same way via `useGitHubRepos.js` → `/api/repos` (`api/repos.js`, shared logic in `api/_repos.js`, cached 30 minutes). GitHub *does* send CORS headers, so the browser could call it directly — the function exists because the unauthenticated limit is 60 requests/hour **per visitor IP**, which one shared network would exhaust; going through the edge means one upstream call serves everyone. Set `GITHUB_TOKEN` in the Vercel environment to raise that ceiling.

**The archive is an allowlist, and this is the one rule to know: a repo listed in `repoOverrides` is on the site; a repo that isn't, isn't.** `isArchived()` in `portfolioData.js` is the only place that decides, and both consumers import it — the runtime hook and `scripts/refresh-repos.mjs` — so the live render and the baked fallback can't disagree. It used to be the reverse (every public repo appeared unless flagged `hidden: true`), and that is what filled the section with coursework, assignments, and repos whose first and last commit were minutes apart; the cut from 21 rows to 9 is what the rule is protecting. GitHub still supplies each listed repo's description, language, stars, dates and homepage, so those stay current on their own and a deleted repo drops out — but a **new** repo stays off until it is written about. `hidden` no longer exists: to remove a repo, delete its entry. Three knobs shape the result, all in `portfolioData.js`:
- **`repoOverrides` (keyed by exact repo name) is both the membership list and where per-repo polish goes** — `title`, `description`, `category`, `language`, `live`. Any field you set wins over GitHub; anything you leave out stays automatic, and `{}` is a valid entry meaning "show this, GitHub's own words are fine". Adding a tenth entry is a claim that the repo shows something the three case studies don't — that is the bar the nine were chosen against.
- **`archiveCategories` is the filter order**, rendered as chips above the grid. A repo with no `category` override lands in `archiveDefaultCategory`, so a brand-new repo always has a home. Categorising rather than bucketing by year is on purpose: nearly every repo shares a creation year, so year buckets would be one long list and one orphan. The archive is a **three-column grid of compact cards**, not one row per repo: 21 repos as hairline rows ran 1,931px (2.1 screens) with the middle column wrapping to three lines and the right third empty; the grid fits them in ~1,150px, and filtering makes the section *shorter* instead of scrolling further. Descriptions are `line-clamp: 3` so every card in a row is the same height. The hook returns one flat `items` list (newest push first) plus `categories` counts — grouping is a render concern now, not a data one.
- **`archiveFallback` is a fallback, not the source of truth** — the same role `posts` plays for writing. `npm run refresh:repos` re-bakes it, applying the same featured/hidden exclusions the site applies at runtime.

`vite.config.js`'s `API_ROUTES` array mounts every `api/` handler during `npm run dev`; add a route there when you add a function, or local dev will silently render the fallback.

**Styling: Tailwind v4 with CSS-first theming.** There's no `tailwind.config.js` — theme tokens (colors, fonts, shadows) are declared via `@theme` in `src/index.css` and consumed both as CSS vars (`var(--color-accent)`) and as generated Tailwind utility classes (`bg-bg`, `text-text-primary`, `border-border`, etc., derived from the `--color-*` names). The Vite plugin `@tailwindcss/vite` handles the build (see `vite.config.js`). When introducing a new color/font/shadow, add it to the `@theme` block rather than hardcoding hex values, so it stays usable as a utility class.

**The decorative layer must never touch the reading column.** Two components draw behind the content, and both are constrained by the same idea — the text column is off limits, and a decoration with nowhere legal to go is dropped rather than squeezed.

- **`PixelModels.jsx`** parks its floaters in the side gutters. `edgeFor(z, radius)` returns `null` when a shape's bounding sphere can't clear `.content-container` at that depth, and `GutterFloater` renders nothing for a `null`. Both the frame and the content column widen with depth, so the content edge is scaled by `(CAM_Z - z) / CAM_Z` before the comparison — skipping that scale is what used to park an invader on the third bullet at 1280px. `CONTENT_MAX_PX` mirrors `.content-container`'s max-width; keep them in sync.
- **`SectionPath.jsx`** routes its ribbon down one gutter per section and swings across only in the band spanning a divider. The route is **a function of page y, not a list of points**: `x(y) = cx + side(y) · lane(y)`, where `side` holds at ±1 through a section and eases to the other side across a boundary, and `lane` is how far out in the gutter it rides. `buildPath` then cuts that function into Bézier segments using its exact slope at each end, so the drawn curve *is* the function. The point-list version it replaced needed a rail point 104px inside every section edge to stop the spline cutting one diagonal from a section's centre to the next's — a full-width gash through a 5,500px section — and needed every control point clamped into its own segment's box to stop the rails bulging out under the dock nav. Those two rules fought each other at the join: the tangent jumped from 0° to 62° in a single step at both ends of every crossing, twelve corners down the page, which is what "the ribbon takes sharp turns" was.

  Five things keep the route and the car from looking wrong, all measured rather than guessed:

  - **The car is driven by page `y`, not by route fraction.** The route is far longer than the page is tall (~14.6k of stroke over ~10.8k of page — every swing buys distance without descending), so interpolating along the stroke made the car stall through crossings and sprint down straights, wandering ±290px up and down the viewport. A 512-entry length↔y sample table, built once per measure, inverts y back to a fraction; the car now holds its height on screen to within ~190px over the whole page.
  - **`MAX_NODE_GAP` subdivides tall sections.** One waypoint per section put a single dot in the middle of a 5,190px straight through `#projects` while short sections got one every 900px. Extra nodes go **along the section's own rail**, so subdividing never adds a crossing. Waypoint spacing went from 1,000–3,325px to 1,000–1,500px. Giving the featured track and the archive a route stop each is the tempting alternative and is worse — those boxes butt against each other's content with no padding, so the swing crossed the section heading on the way in and the last row of archive cards on the way out.
  - **`MAX_DWELL_PX` caps the dwell at 110px.** A dwell freezes the car in *document* space, so every pixel of it slides the car up the viewport. The old proportional dwell (28% of the gap to the nearest node) came to 896px around `#projects` — the car left the top of the screen entirely, then raced back down to catch up.
  - **A crossing is sized by the part of it that is over the text, not by the whole swing.** Its ends are out in the gutter, where the ribbon is free at any y, so only the middle has to fit the empty band between two sections — and that band is each section's own padding, read from `getComputedStyle` (144px on about/skills/projects, 128 on github/writing, 176 on contact) rather than the flat 104 the rail points guessed at. A 325px gap therefore carries a ~600px swing. `overTextSpan` measures what the route actually spends over the column and the swing is scaled to fit in three passes, which beats solving it in closed form: the closed form has to be redone for every change to the curve and cannot see the lane drift at all. Measured over the same page, the steepest point of a crossing went from 14.8px sideways per px down to 4.2, and the tightest bend from a 2px radius (i.e. a corner) to 77px.
  - **The crossing eases with smootherstep, not a raised cosine.** Both meet the straight at zero slope; only smootherstep also arrives with zero *curvature*, so the ribbon opens out of the rail instead of bending off it. A raised cosine put the tightest bend of the whole route right where the eye is following a straight line. It pays with a faster middle, which costs nothing here — a faster middle spends less time over the text, which is the only thing the swing is rationed on. Segment y-values are evenly spaced by construction, so y is monotonic along the path and the length↔y inversion keeps working without anything being clamped.

  The amplitude is derived from the text column and the dock, not from a fraction of the width: `lo` is the text edge plus clearance, `hi` is short of the dock nav, and the ribbon's mean position sits 72% of the way toward `hi`. The old `min(w*0.4, w/2 - 130)` knew about the dock but nothing about the text, and put the ribbon 79px *inside* the reading column at 1024px. `lane` then drifts slowly across whatever room is left either side of that mean (`DRIFT_LEN` is its wavelength), so a straight bows the way a drawn line does instead of ruling itself against an invisible edge — ±25px at 1440px, more on a wider screen, and nothing at all below ~1100px where there is no lane to spare. Because the drift is bounded by the same `lo`/`hi`, it can reach neither the text nor the dock.

`index.css` also holds a number of hand-written component classes used across sections instead of Tailwind utility soup: `.spotlight-card`, `.dock-nav` / `.dock-nav-item`, `.tag-chip`, `.cta-button` / `.cta-button-ghost`, `.section-label`, `.section-title`, `.content-container`, `.section-divider`, `.project-card` / `.project-card__inner` / `.track-mask` / `.track-tick`, `.metric-stack` / `.metric-item` / `.metric-value` / `.metric-label`, `.archive-filters` / `.archive-chip` / `.archive-grid` / `.archive-card`, plus one-off effects (`.grain-overlay`, `body.screen-shake`, `body.sidebar-open`). Reuse these classes for new sections rather than re-implementing the same look with raw utilities.

**Custom cursor changes global cursor behavior.** `index.css` sets `cursor: none !important` on all elements at `@media (pointer: fine)`, and `CustomCursor.jsx` renders the replacement cursor itself — any new interactive element should still declare correct `cursor-*` intent classes for non-fine-pointer devices, but expect the visual cursor on desktop to come from that component, not native styling.

**Animation convention (Framer Motion).** Scroll-triggered reveals use `whileInView` with `viewport={{ once: true, margin: '-50px' }}` (see `Card.jsx`, the shared wrapper used by most section content blocks). Entrance sequences (Navbar, Hero) use staggered `initial`/`animate` with explicit `delay`. Follow this pattern rather than introducing a different animation approach for new sections.

**Easter egg / mini-game.** Typing "play" anywhere on the page (`EasterEgg.jsx`, global `keydown` listener buffering the last 4 keys) opens a modal hosting `RetroCarGame.jsx`, a self-contained canvas-based game component. Treat it as an isolated feature — it doesn't share state with the rest of the app beyond the open/close modal wrapper.

**No routing, no global state.** All interactivity is local `useState`/`useEffect` per component (scroll-spy in `Navbar`, keyboard buffer in `EasterEgg`, etc.). Don't reach for a router or a context/store for new features unless the scope genuinely outgrows this — the codebase deliberately has neither.
