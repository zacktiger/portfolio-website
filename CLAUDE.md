# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

A single-page personal portfolio site (Kshitij Bachhav) built with React 19 + Vite + Tailwind CSS 4, animated with Framer Motion. No backend, no router, no state library — it's one scrollable page assembled from section components.

## Commands

- `npm run dev` — start Vite dev server (default `http://localhost:5173`)
- `npm run build` — production build to `dist/`
- `npm run preview` — serve the production build locally
- `npm run refresh:posts` — re-bake the offline copy of the Medium posts into `portfolioData.js` (optional; the live site doesn't depend on it)
- `npm run refresh:repos` — re-bake the offline copy of the GitHub project archive into `portfolioData.js` (optional; same deal)

## Pages

Two Vite entries (see `build.rollupOptions.input` in `vite.config.js`): the main site (`index.html` → `src/main.jsx`) and a standalone resume page (`resume.html` → `src/resume.jsx` → `ResumePage.jsx`). The resume is typeset from `portfolioData.js` and has a print stylesheet (`src/components/resume.css`) — "Download PDF" is just `window.print()`. The main site hides the native cursor globally for `CustomCursor`; `resume.css` restores it on the resume page, so any new page without `CustomCursor` needs the same override.

There is no lint script, no test runner, and no TypeScript configured in this repo.

## Architecture

**Single-page composition.** `src/App.jsx` renders one document: `Navbar`, then a `<main>` with `Hero → About → Skills → Projects → Contact` sections separated by a `Divider`, then `Footer`, plus fixed-position overlay components (`CustomCursor`, `EasterEgg`) mounted at the root. Sections are plain `<section id="...">` elements; the id (`home`, `about`, `skills`, `projects`, `contact`) is the anchor used for both nav scroll-spy and `scrollIntoView` navigation — keep those ids in sync between `Navbar.jsx`'s `navItems` and each section component.

**Content lives in data, not JSX.** `src/data/portfolioData.js` is the single source of truth for skills, featured projects, achievements, and contact info (email/LinkedIn/GitHub) — it's a plain JS module exporting arrays/objects consumed by `Skills.jsx`, `Projects.jsx`, and `Contact.jsx`. To add/edit a featured project or skill category, edit this file, not the component markup. Project entries reference images by path (e.g. `/project-saas.png`) served from `public/`.

**The projects section is two tiers, and only the top one is authored.** `projects` holds the three case studies the resume leads with; each is built around a `metrics` array of exactly three measurements, because this work is backend and a screenshot would misrepresent where the effort went. `image` is optional and is **the one element on a card allowed to change size**: it renders low in the prose column, after the bullets and before the tags, and carries `flex: 1 1 auto; min-height: 0` so it absorbs the difference between a case study's natural height and the single height the whole track is laid out to. That is what lets three cards share one height without a word of prose being clipped — a short window drops the picture, never the sentence (`.project-card__figure` hides it under `max-height: 780px`). It used to sit between the opening line and the bullets, which put a screenshot in front of the point it was meant to support and made that card 35% taller than its siblings. Everything else is the archive below it, which is generated — see the next section. A featured project's `repo` field must match its GitHub repository name exactly; that's what keeps it from also appearing in the archive.

Each case study is a **bounded card on a pinned horizontal track** (`FeaturedScroller.jsx`): a wrapper N×100vh tall holds a sticky viewport-height frame, and scroll progress through it drives the track's `translateX`, so scrolling down moves the cards sideways. Inside a card the layout is unchanged — identity, date, stack and the three metrics on the left; description, bullets, tags and links on the right.

Three constants carry the design, and each is there because its absence looked broken:

- **`CARD_MAX` / `LANE`.** A card is capped at 980px and never wider than `vw - 2 × LANE`. Full-bleed 100vw cards were the original bug: with no edges, mid-transition you saw one case study's prose beside the next one's metric rail with nothing between them, which reads as a broken page rather than as two cards passing. `LANE` is 190px because the SectionPath ribbon and the dock nav both live out there — a wider card put its metric labels behind the dock icons. The cap is deliberately *narrower* than `.content-container`'s 1100px measure: the card is a panel sitting inside the page, so matching the page's own measure made it read as the page rather than as an object on it, and left less room for the neighbour to peek.
- **`RESERVE` / `CARD_H_MAX` / `CARD_H_MIN` — every card in the track is laid out to ONE height, and this is a correctness rule, not a nicety.** The cards do not naturally want the same height: the one with an `image` measured 857px against 637px for the two without, and in a frame where cards slide *past* each other a 220px difference reads as the frame itself jolting. Worse, the frame is `overflow-hidden` and exactly one viewport tall, so at 1366×768 that card came to 894px, hung 63px off each end, and had its opening line sliced in half and its Code / Live Demo links cut off with no way to scroll to them. So the height comes from the viewport (`vh - RESERVE`, capped at `CARD_H_MAX`) and never from the tallest card's content. `RESERVE` is 168px because the progress ticks sit at `bottom: 40px` and are ~21px tall — anything less put the tick bar *on* the card, drawing it straight through the tag line. Below `CARD_H_MIN` there is no height worth pinning to and the component falls back to the vertical stack.
- **`MOVE`.** The scroll→track map is detented, not linear: each card holds its centred position for a stretch of scroll and the moves happen in between. That reads as snapping without taking the scroll away from the user. `MOVE` is the budget — each of the `total - 1` transitions gets 18% of the track's scroll and everything left over is stillness, split equally between the cards. With three cards that is **65% of the section during which scrolling advances the page and moves nothing**, so a reader can work through a case study at their own pace without the thing they are reading sliding out from under them. Deriving the holds from evenly-spaced card centres instead is what left only 44%, and made every scroll gesture move the cards. The track deliberately does **not** auto-advance — auto-forwarding carousels measurably hurt comprehension, and anything self-moving past five seconds owes the user a pause control (WCAG 2.2.2). The progress ticks under the track are that control instead: click one to scroll to that card.
- **The opacity/scale falloff is flat through the middle and steep at the edges** (`[i-1, i-0.6, i, i+0.6, i+1]`). A linear ramp dimmed *both* cards to ~60% halfway through a move — the whole screen went dark at the moment there was most to look at. The dim's job is to mark the subject when a card is parked off-centre; mid-move there is no subject.

`.track-mask` fades the track's outer 190px — `LANE`, so the mask and the width cap come from the same clearance — so the peeking neighbour dissolves into the gutter instead of sliding under the dock nav. The fade has to be measured against where the dock actually *starts*, not merely be wider than the dock: its near edge is 82px in (58px wide at a 24px offset), and the old 120px ramp was still at 67% opacity there, which is why a card's prose stayed legible straight through the icons mid-slide. It must sit on a **static** wrapper: a mask painted on the moving track would travel with it and fade the middle of a card as it passed.

Below `lg`, under `prefers-reduced-motion`, and before hydration, the same cards render as a plain vertical stack — a viewport-width card on a phone is unreadable and horizontal pinning fights touch scrolling. Known cost, stated plainly: off-screen cards are translated out of view rather than unmounted, so find-in-page can't usefully scroll to them and tabbing into one jumps the page. That's inherent to the pattern, not to this implementation.

**Two sections are live, not authored: writing and the project archive.** Both follow the same shape — a Vercel function under `api/`, an edge cache, a `use*` hook, and a build-time fallback in `portfolioData.js`. `Writing.jsx` renders whatever is on Medium right now. `useMediumPosts.js` fetches `/api/medium`, a Vercel serverless function (`api/medium.js`) that reads the RSS feed **server-side** — medium.com sends no `Access-Control-Allow-Origin` header, so the browser can never fetch that feed directly, and every public CORS proxy is rate-limited or intermittent. The response is cached at Vercel's edge for 5 minutes with `stale-while-revalidate`, so a newly published article appears within ~5 minutes with no edit and no redeploy.

Three consequences worth knowing before touching this area:
- **`posts` in `portfolioData.js` is a fallback, not the source of truth.** It renders instantly on load and stays on screen if the feed request fails, so the section is never empty. Editing it does not change what a visitor normally sees.
- **`postOverrides` (keyed by canonical article URL) is where per-post polish goes** — a better `tag` or `blurb` than Medium's own. It is merged over both live and fallback posts, so the two render identically. Feed `<category>` slugs are title-cased automatically (`crude-oil` → `Crude Oil`).
- **`api/_feed.js` is shared** by the serverless function, the dev middleware, and `scripts/refresh-posts.mjs` — parse fixes belong there. The leading underscore is what stops Vercel from routing it as its own endpoint. `vite.config.js` mounts that same handler at `/api/medium` during `npm run dev`, so local dev exercises the real path instead of silently falling back.

`Projects.jsx`'s archive works the same way via `useGitHubRepos.js` → `/api/repos` (`api/repos.js`, shared logic in `api/_repos.js`, cached 30 minutes). GitHub *does* send CORS headers, so the browser could call it directly — the function exists because the unauthenticated limit is 60 requests/hour **per visitor IP**, which one shared network would exhaust; going through the edge means one upstream call serves everyone. Set `GITHUB_TOKEN` in the Vercel environment to raise that ceiling.

**The archive is an allowlist, and this is the one rule to know: a repo listed in `repoOverrides` is on the site; a repo that isn't, isn't.** `isArchived()` in `portfolioData.js` is the only place that decides, and both consumers import it — the runtime hook and `scripts/refresh-repos.mjs` — so the live render and the baked fallback can't disagree. It used to be the reverse (every public repo appeared unless flagged `hidden: true`), and that is what filled the section with coursework, assignments, and repos whose first and last commit were minutes apart; the cut from 21 rows to 9 is what the rule is protecting. GitHub still supplies each listed repo's description, language, stars, dates and homepage, so those stay current on their own and a deleted repo drops out — but a **new** repo stays off until it is written about. `hidden` no longer exists: to remove a repo, delete its entry. Three knobs shape the result, all in `portfolioData.js`:
- **`repoOverrides` (keyed by exact repo name) is both the membership list and where per-repo polish goes** — `title`, `description`, `category`, `language`, `live`. Any field you set wins over GitHub; anything you leave out stays automatic, and `{}` is a valid entry meaning "show this, GitHub's own words are fine". Adding a tenth entry is a claim that the repo shows something the three case studies don't — that is the bar the nine were chosen against.
- **`archiveCategories` is the filter order**, rendered as chips above the grid. A repo with no `category` override lands in `archiveDefaultCategory`, so a brand-new repo always has a home. Categorising rather than bucketing by year is on purpose: nearly every repo shares a creation year, so year buckets would be one long list and one orphan. The archive is a **three-column grid of compact cards**, not one row per repo: 21 repos as hairline rows ran 1,931px (2.1 screens) with the middle column wrapping to three lines and the right third empty; the grid fits them in ~1,150px, and filtering makes the section *shorter* instead of scrolling further. Descriptions are `line-clamp: 3` so every card in a row is the same height. The hook returns one flat `items` list (newest push first) plus `categories` counts — grouping is a render concern now, not a data one.
- **`archiveFallback` is a fallback, not the source of truth** — the same role `posts` plays for writing. `npm run refresh:repos` re-bakes it, applying the same featured/hidden exclusions the site applies at runtime.

`vite.config.js`'s `API_ROUTES` array mounts every `api/` handler during `npm run dev`; add a route there when you add a function, or local dev will silently render the fallback.

**Styling: Tailwind v4 with CSS-first theming.** There's no `tailwind.config.js` — theme tokens (colors, fonts, shadows) are declared via `@theme` in `src/index.css` and consumed both as CSS vars (`var(--color-accent)`) and as generated Tailwind utility classes (`bg-bg`, `text-text-primary`, `border-border`, etc., derived from the `--color-*` names). The Vite plugin `@tailwindcss/vite` handles the build (see `vite.config.js`). When introducing a new color/font/shadow, add it to the `@theme` block rather than hardcoding hex values, so it stays usable as a utility class.

**The decorative layer must never touch the reading column.** Two components draw behind the content, and both are constrained by the same idea — the text column is off limits, and a decoration with nowhere legal to go is dropped rather than squeezed.

- **`PixelModels.jsx`** parks its floaters in the side gutters. `edgeFor(z, radius)` returns `null` when a shape's bounding sphere can't clear `.content-container` at that depth, and `GutterFloater` renders nothing for a `null`. Both the frame and the content column widen with depth, so the content edge is scaled by `(CAM_Z - z) / CAM_Z` before the comparison — skipping that scale is what used to park an invader on the third bullet at 1280px. `CONTENT_MAX_PX` mirrors `.content-container`'s max-width; keep them in sync.
- **`SectionPath.jsx`** routes its ribbon down one gutter per section and swings across only in the band spanning a divider. `pathPts` adds a rail point `CROSS_HALF` (104px) inside each section's top and bottom at the same x; without them the spline cut a single diagonal from one section's centre to the next's, a full-width gash through a 5,500px section. That inset has to stay under the ~112px of section padding — that padding is the only reason the swing crosses air instead of paragraphs.

  Four things keep the car itself from looking wrong, all measured rather than guessed:

  - **The car is driven by page `y`, not by route fraction.** The route is far longer than the page is tall (~16.9k of stroke over ~10.7k of page — every swing buys distance without descending), so interpolating along the stroke made the car stall through crossings and sprint down straights, wandering ±290px up and down the viewport. A 512-entry length↔y sample table, built once per measure, inverts y back to a fraction; the car now holds its height on screen to within ~190px over the whole page.
  - **`MAX_NODE_GAP` subdivides tall sections, and the stroke is routed THROUGH those nodes.** One waypoint per section put a single dot in the middle of a 5,190px straight through `#projects` while short sections got one every 900px. Extra nodes go **along the section's own rail**, so subdividing never adds a crossing. The path is built from the same node list the car stops at, so each one is a place the route actually turns — previously the stroke ran enter→mid→exit and the subdividing waypoints were dots sitting *on* a dead-straight line rather than bends in it. Giving the featured track and the archive a route stop each is the tempting alternative and is worse — those boxes butt against each other's content with no padding, so the swing crossed the section heading on the way in and the last row of archive cards on the way out.
  - **`CAR_SEAT` — the car does not travel down the viewport at all.** It holds one seat (mid-screen) and the route flows past it: its document position is simply `scrollY + CAR_SEAT × vh`, which makes its screen position exact *by construction* rather than something the scroll mapping has to be tuned to preserve. Measured drift over the whole page: **1px**.

    This replaced a scroll→y keyframe table with a "dwell" window at each waypoint, and that history is worth knowing before anyone reintroduces one. The intent was a beat at each node, but a dwell holds the car still in *document* space, so every pixel of it slid the car up the viewport and the catch-up slid it back down — a measured **557px** sawtooth. Softening the flat into a slow creep only halved it (→287px). It could not be tuned away, because the problem is structural: **any mapping whose y advances at a rate other than the scroll rate moves the car on screen**, so the identity map is the only one that holds it still. What now reads as motion is the route sliding past and the car steering into the bends — both of which survive the pinned card track, where the page behind the car isn't scrolling either and a car that also held its document position had nothing at all to move against.

    Two consequences that are easy to undo by accident:
    - **The car is driven off raw `scrollY`, not a spring.** A spring is a lag and a lag is movement — it let the car sag down the screen during a fast scroll and float back up when it stopped. The ribbon's draw comes off the car's own position, so there is nothing left to smooth.
    - **The LEAD offset is applied to the trail, not to the car.** Pushing the car forward along the path to make it look like it's pulling its trail gives that offset a *vertical* component on any diagonal, which was 40px of leftover bob on a 768px window. Ending the trail `LEAD` short of the car gives the same gap with the car's y untouched.
    - **The route runs to the foot of the page**, not to the middle of `#contact`. The car needs route to exist down to `h - vh/2`; ending short of that clamps it, and a clamped car slides up the screen over the last few hundred pixels of scroll.
  - **The rails wander (`WANDER` / `WAVE_PX`), so the route curves instead of ruling.** Each waypoint's x is nudged along a slow sine of its page position, by a fraction of `hi - lo` — the same two bounds the rail position itself is derived from, so no phase of the wave can reach text or reach the dock. Dead-vertical rails gave `#projects` 2,700px of unbroken straight stroke, which is a large part of why the car looked motionless there even while it was moving: a straight line offers nothing to move against. Where the viewport is too narrow for a clean lane (`hi < lo`) there is nothing to wander inside and the route stays on its rail, exactly as before.
  - **`buildPath` clamps each Bézier control point to its own segment's bounding box.** Plain Catmull-Rom takes its tangent from the neighbours either side, so at a right-rail waypoint the previous left-rail one dragged the curve ~89px past the rail, straight under the dock nav. Clamping also guarantees the monotonic y that the length↔y inversion depends on.

  The amplitude is derived from the text column and the dock, not from a fraction of the width: `lo` is the text edge plus clearance, `hi` is short of the dock nav, and the swing sits 72% of the way toward `hi`. The old `min(w*0.4, w/2 - 130)` knew about the dock but nothing about the text, and put the ribbon 79px *inside* the reading column at 1024px.

`index.css` also holds a number of hand-written component classes used across sections instead of Tailwind utility soup: `.spotlight-card`, `.dock-nav` / `.dock-nav-item`, `.tag-chip`, `.cta-button` / `.cta-button-ghost`, `.section-label`, `.section-title`, `.content-container`, `.section-divider`, `.project-card` / `.project-card__inner` / `.project-card__figure` / `.track-mask` / `.track-tick`, `.metric-stack` / `.metric-item` / `.metric-value` / `.metric-label`, `.archive-filters` / `.archive-chip` / `.archive-grid` / `.archive-card`, plus one-off effects (`.grain-overlay`, `body.screen-shake`, `body.sidebar-open`). Reuse these classes for new sections rather than re-implementing the same look with raw utilities.

**Clicking a project card sparks; it does not shake or flash.** `CustomCursor`'s `shoot` handler used to add `body.screen-shake` for 80ms and dispatch a `laser-hit` that ran a `filter: brightness(1.6)` flash across the card for 350ms. Because a card's own Code / Live Demo links sit inside `[data-project-id]`, that fired when someone was simply following a link — a page that jolts and flashes as you click through it reads as a rendering fault rather than as feedback. Only the cursor-local particle burst remains.

**Custom cursor changes global cursor behavior.** `index.css` sets `cursor: none !important` on all elements at `@media (pointer: fine)`, and `CustomCursor.jsx` renders the replacement cursor itself — any new interactive element should still declare correct `cursor-*` intent classes for non-fine-pointer devices, but expect the visual cursor on desktop to come from that component, not native styling.

**Animation convention (Framer Motion).** Scroll-triggered reveals use `whileInView` with `viewport={{ once: true, margin: '-50px' }}` (see `Card.jsx`, the shared wrapper used by most section content blocks). Entrance sequences (Navbar, Hero) use staggered `initial`/`animate` with explicit `delay`. Follow this pattern rather than introducing a different animation approach for new sections.

**Easter egg / mini-game.** Typing "play" anywhere on the page (`EasterEgg.jsx`, global `keydown` listener buffering the last 4 keys) opens a modal hosting `RetroCarGame.jsx`, a self-contained canvas-based game component. Treat it as an isolated feature — it doesn't share state with the rest of the app beyond the open/close modal wrapper.

**No routing, no global state.** All interactivity is local `useState`/`useEffect` per component (scroll-spy in `Navbar`, keyboard buffer in `EasterEgg`, etc.). Don't reach for a router or a context/store for new features unless the scope genuinely outgrows this — the codebase deliberately has neither.
